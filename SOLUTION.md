`result.json` получен строго по шагам из TASK.md, скрипт для повтора: `bash scripts/make-result.sh`.

## 1. Скидки

- Новая колонка `orders.amount_paid_kop` (копейки, `NULL` у заказов, сохранённых до появления поля).
- Источник правды для `net` - `amountPaid` из API ("сколько клиенты фактически заплатили"). `discountPercent` не храню: пересчёт процента дал бы вопрос округления, а `amountPaid` уже и есть списанная сумма. Проверил на данных: у всех 3853 заказов с полями `amountPaid == amount * (1 - discountPercent / 100)` до копейки.
- Все суммы считаются в копейках (целые), в рубли переводятся только в ответе. `discount = gross - net` тоже считается в копейках, поэтому `gross - net` в ответе сходится без хвостов float.
- `total` оставлен и равен `gross`.

## 2. Жалоба по c_7 (27-31.03)

**Причина.** `TotalsService.daily` брал смещение таймзоны клиента один раз на текущий момент: `tzOffsetMinutes(timezone, new Date())`. У c_7 таймзона `Europe/Berlin`, а 29.03.2026 в 01:00 UTC там переход с UTC+1 на UTC+2. Сейчас (ноябрь) смещение +1, поэтому заказы после перехода, сделанные между 22:00 и 23:00 UTC (это 00:00-01:00 по Берлину следующего дня), попадали в предыдущий день. До 29.03 смещение +1 верное, поэтому 27 и 28 сходились, а 29-31 нет. Летом ошибка была бы зеркальной: поехали бы дни до перехода. То есть результат зависел от даты, когда запущен сервис.

**Исправление.** Смещение считается для каждого заказа на его `createdAt`: `dateAtOffset(o.createdAt, tzOffsetMinutes(timezone, o.createdAt))`.

**Как нашёл.**
1. Выгрузил все 5030 заказов из API и разобрал заказы c_7 за 25.03-01.04. У c_7 есть заказы около полуночи по Берлину (21:10, 22:15, 22:40, 23:20 UTC и т. д.), значит, ошибка при определении дня быстро проявится.
2. "Часть дней" плюс "конец марта" плюс европейская таймзона - это переход на летнее время. В коде смещение берётся на `new Date()`.
3. Проверил расчётом: старая логика (UTC+1 всегда) даёт gross 43964 / 52201 / 44064 за 29/30/31, правильная (zoneinfo) - 34658 / 59684 / 35401. 27 и 28 совпадают.
4. Заодно проверил вторую гипотезу: что даты без зоны (`"2026-03-27T00:30:46"`, 288 заказов, у c_7 их больше всех, 36) на самом деле в местном времени клиента, а не в UTC. Не подтвердилась: `updatedAt - createdAt` у них ни разу не отрицательный и распределён так же, как у дат с `Z` (если бы это было местное время Берлина, задержки сместились бы на 1-2 часа). Оставил трактовку "без зоны = UTC".

Тест: `test/totals.test.ts`, "день считается по смещению таймзоны на момент заказа". Заказы по обе стороны перехода, поэтому старая логика падает при любой текущей дате.

## 3. Гонка при вебхуках

При первой сборке `result.json` gross сошёлся с расчётом, а net за 30 и 31 нет (разница ровно 1357.92 и 2207.54). Это заказы `o_02362` и `o_02455`, по которым вебхуки меняют скидку: 0% -> 10% (02:15) -> 33% (03:15). В БД осталась версия 02:15.

Мок шлёт 92 вебхука примерно за 4 секунды параллельно, с дублями (до 6 копий одного события) и не по порядку. `OrdersService.apply` делал "прочитать текущую версию -> сравнить `updatedAt` -> записать" без блокировки. Два запроса по одному заказу одновременно видят старую версию, оба проходят проверку, и остаётся тот, кто записал последним.

**Исправление.** Сравнение и запись - один запрос: `INSERT ... ON CONFLICT DO UPDATE ... WHERE orders.updated_at < excluded.updated_at`, результат (`created` / `updated` / `stale`) по `RETURNING (xmax = 0)`. Тест `test/webhooks.test.ts` шлёт пачку параллельных дублей двух версий. На старой логике он падает (остаётся старая версия), на новой проходит.

## 4. Копейки

`toKop` делал `Math.floor(rub * 100)`. `4549.23 * 100` в float даёт `454922.99999999994`, и `floor` отбрасывает целую копейку. Таких сумм в данных 96, у c_7 они есть 28, 29 и 30.03 (в `amountPaid`, поэтому на `net`). Теперь сначала убирается шум float (`toFixed(6)`), потом отбрасываются доли копейки. Старый тест "отбрасывает доли копейки" (`10.999 -> 1099`) по-прежнему проходит.

## 5. Заказы, сохранённые до появления скидок

Если сервис уже работал до появления `amountPaid`, у старых заказов колонка `NULL`. Повторный синк их бы не обновил: API добавил поле, не меняя `updatedAt`, и версия считалась бы устаревшей. Поэтому та же версия (`updatedAt` равен), в которой появился `amountPaid`, тоже записывается. Более старая версия с `amountPaid` по-прежнему не перетирает более новую (тест на это есть). Пока заказ не дозаполнен, `net = gross`.

## 6. Мелкие улучшения

- `HttpOrdersApi`: ретраится только `200 {"error":"rate_limited"}`. Любая другая ошибка в теле `200` сразу становится `UpstreamError` с текстом ответа. Раньше она 8 раз ретраилась, и причина терялась за "no successful response". На клиент тестов не было, добавил `test/orders-api.test.ts` (fetch подменяется).
- `sync_runs` хранит `applied` / `stale` / `invalid` (миграция `003`). Раньше записывались только `pages` / `received`, а для разбора инцидентов нужнее остальное.
- Смещение таймзоны теперь считается на каждый заказ, поэтому `Intl.DateTimeFormat` кэшируется по таймзоне: создавать его на каждый вызов дорого.

## Что ещё заметил

**Внешний API**
- Пагинация по смещению: курсор - это base64 от `o:100`, `o:200`... Если во время синка появятся новые заказы, страницы сдвинутся, и что-то можно пропустить или получить дважды. Лучше курсор по `(updatedAt, id)`, это вопрос к команде API.
- Конец списка: пустая страница с тем же курсором вместо `nextCursor: null` (уже учтено в коде).
- Rate limit иногда приходит как `200 {"error":"rate_limited"}` (поймал 3 раза за полную выгрузку).
- Типы плавают: `amount` бывает строкой (`"3100.00"`, 157 шт.), `discountPercent` тоже (`"7"`, 177 шт.), `createdAt` иногда без зоны (288 шт.). `updatedAt` всегда с `Z`.
- `amountPaid`/`discountPercent` есть только у заказов с 15.03.2026. У более ранних их нет.
- Вебхуки (все по c_7): дубли, не по порядку, параллельно. Скидка меняется **после** оплаты (`o_02362`: оплачен с 0%, потом 10%, потом 33%). Технически это обрабатывается, но стоит спросить у бизнеса, нормально ли это.
- `o_049xx`-`o_050xx` созданы в марте, а `updatedAt` у них на дни и недели позже (до 20 дней). Синк их забирает, просто отмечаю как особенность.

**Код**
- Таймзона клиента кэшируется навсегда. Если клиент сменит таймзону, сервис об этом не узнает (если узнает, вся история пересчитается по новой зоне).
- `/webhooks/order` без аутентификации и подписи: кто угодно может прислать заказ.
- `daily-totals` не ограничивает длину периода: `from=1900-01-01&to=2100-12-31` - это 73 тыс. дней в ответе.
- День заказа считается по `createdAt`, а не по дате оплаты, и `refunded` полностью исключается. Значит, возврат задним числом меняет уже отданные цифры за прошлые дни.

## Допущения

- `net` берётся из `amountPaid`, без пересчёта из `discountPercent`.
- Нет `amountPaid` - скидки нет, `net = gross`. Если когда-нибудь придёт `discountPercent > 0` без `amountPaid`, это будет учтено как без скидки (в данных такого нет).
- `amountPaid > amount` - невалидный заказ (`400` для вебхука, `invalid` в статистике синка).
- Дата без зоны - UTC (как и было, гипотезу про местное время проверил и отбросил, см. выше).
- День заказа - по `createdAt` в таймзоне клиента, как и раньше. Жалоба подтверждает, что так считает и платёжная система ("по остальным дням совпадают").
- В трёх существующих тестах `totals` поменял только ожидаемые объекты (добавил `gross`/`discount`/`net`): формат ответа меняется по заданию, сами проверки те же.

## Что бы доделал

- Группировку по дням перенести в SQL: `date(created_at AT TIME ZONE $tz)` - Postgres сам знает правила переходов, и не нужно тащить заказы в приложение.
- Сохранять причины `invalid` при синке (сейчас есть только количество).
- Подпись вебхуков (HMAC) и ограничение длины периода в `daily-totals`.
- e2e-тест с образом мока в CI (то, что делает `scripts/make-result.sh`, плюс сверка с эталоном).

## Как проверял

1. `npm test` - 40 тестов (было 27), `npm run typecheck` чистый.
2. Новые тесты прогнал на старом коде: падают 9 (скидки, переход на летнее время, копейка, дозаполнение). Тест на гонку прогнал на логике "прочитать, сравнить, записать": падает.
3. Независимая сверка `result.json`: выгрузил все заказы из API и перехватил вебхуки своим HTTP-приёмником, применил "последняя версия по `updatedAt`" и посчитал дни в Python (`zoneinfo` + `Decimal`, без кода сервиса). Все 5 дней совпали по `gross`, `net`, `discount` до копейки.
4. `scripts/make-result.sh` (чистая БД -> синк -> вебхуки -> запрос) прогнал 3 раза подряд, ответ одинаковый. До исправления гонки net за 30-31.03 от прогона к прогону мог отличаться.
5. Каждую гипотезу (летнее время, даты без зоны, гонка) сначала подтверждал на данных мока, потом закреплял тестом, который падает на старом коде.
